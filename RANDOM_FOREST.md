# Random Forest: what was done, what each file holds

This is the reference for writing the Random Forest section of the report.
Every number below comes from the files listed here, and every file can be
regenerated by running the six scripts in order.

All results here are **without the compile date** (`hdr_TimeDateStamp`).
Section 4 explains why it was removed and shows the scores from before.

## 1. The two questions the model answers

The dataset (see `DATA.md`) has two labels per file, so we train two separate
Random Forests:

| Task name | Question | Files used | Classes |
|---|---|---|---|
| `binary` | Is this file malware or benign? | all files | 2: Benign, Malware |
| `family` | Which kind of malware is it? | malware files only | 6: RedLineStealer, Downloader, RAT, BankingTrojan, SnakeKeyLogger, Spyware |

Both use the same **299 features**: 222 API-call flags, 38 section fields,
30 header fields and 9 DLL flags. The data files hold 300; the loader
(`src/data.py`) leaves out `hdr_TimeDateStamp` for every model.

| | Training set | Test set |
|---|---|---|
| `binary` | 18,768 files (1,501 benign, 17,267 malware) | 4,693 files (375 benign, 4,318 malware) |
| `family` | 17,267 malware files | 4,318 malware files |

## 2. Ideas needed to read the results

**Decision tree.** A flowchart of yes/no questions about a file ("does it
import this function?", "is this section bigger than X?"). The tree chooses
its own questions during training, each time picking the one that best
separates the classes.

**Random Forest.** Many trees (300 here) that vote. Each tree sees a random
sample of the training files and, at each question, may only pick from a
random subset of the features. The trees make different mistakes, so the
majority vote is more reliable than any single tree.

**Training vs tuning.** Training is the model learning from data. Tuning is us
choosing the model's settings (number of trees, depth, and so on) by trying
several and keeping the best.

**5-fold cross-validation (CV).** A way to score a model using only the
training set. The training set is cut into 5 parts ("folds"); the model is
trained on 4 and quizzed on the 5th, five times, so each part is the quiz
once. Every file is predicted by a model that never saw it. The 5 scores are
averaged. All scripts use the same folds, defined once in `src/evaluation.py`:
`StratifiedKFold(n_splits=5, shuffle=True, random_state=42)`. "Stratified"
means each part keeps the same class proportions as the whole.

**Standard deviation across folds (the "+/-" value).** The 5 fold scores are
never identical, because each fold quizzes on different files. Their standard
deviation measures how much they differ, and so how much of a score is down
to chance. A difference between two models or settings that is no bigger than
this could be chance alone. This is a rule of thumb, not a formal test.

**Test set.** 20% of the data, set aside before any modelling. It is used
only in step 4, after all settings are fixed. Scores on it are the ones to
quote as final results.

**Metrics.**

| Metric | Meaning |
|---|---|
| Accuracy | Share of files classified correctly. Misleading for `binary`, because 92% of files are malware: always answering "malware" already scores 0.92. |
| Precision (per class) | Of the files the model labelled as this class, the share that really are. |
| Recall (per class) | Of the files that really are this class, the share the model found. |
| F1 (per class) | One number combining precision and recall. It is high only when both are. |
| Macro-F1 | The plain average of the per-class F1 scores. Every class counts equally, however rare. **This is the main metric in this project**, and the one tuning optimised. |
| ROC-AUC (`binary` only) | How well the model's confidence ranks malware above benign; 1.0 is perfect, 0.5 is guessing. |
| Confusion matrix | A table of true class (rows) against predicted class (columns). The diagonal is correct predictions; everything else is a specific kind of mistake. |

## 3. The six steps and their results

### Step 1. Baseline (`src/random_forest/baseline.py`)

Mostly default settings: 300 trees, `class_weight="balanced"`, everything
else scikit-learn's default. Scored by 5-fold CV. It also scores a "dummy"
model that always answers with the most common class, as the floor any real
model must beat.

| Task | Dummy accuracy | Dummy macro-F1 | RF accuracy | RF macro-F1 (+/- across folds) |
|---|---|---|---|---|
| `binary` | 0.9200 | 0.4792 | 0.9772 | 0.9148 (+/- 0.0035) |
| `family` | 0.2231 | 0.0608 | 0.8158 | 0.8219 (+/- 0.0054) |

### Step 2. Tuning (`src/random_forest/tune.py`)

Randomized search: 30 random combinations of settings per task, each scored by
the same 5-fold CV on macro-F1 (150 trainings per task).

| Setting | Values offered | Meaning |
|---|---|---|
| `n_estimators` | 300, 500 | number of trees |
| `max_depth` | None, 20, 30, 40 | how many questions deep a tree may go (None = no limit) |
| `min_samples_leaf` | 1, 2, 4 | smallest group of files a tree may end on |
| `min_samples_split` | 2, 5, 10 | smallest group a tree may split further |
| `max_features` | sqrt, log2, 0.1, 0.2 | share of features each question may choose from |
| `criterion` | gini, entropy | formula for judging a question's quality |
| `class_weight` | balanced, balanced_subsample, None | whether rare classes count for more |

| Task | Baseline | Best of 30 | Worst of 30 |
|---|---|---|---|
| `binary` | 0.9148 | 0.9191 | 0.8210 |
| `family` | 0.8219 | 0.8278 | 0.7733 |

The same combination won both tasks. Tuning gained about half a point, close
to the standard deviation across folds (0.004); poor settings cost far more
(5 to 9 points), so the defaults were already close to the best.

### Step 3. Follow-up on `max_features` (`src/random_forest/max_features.py`)

The winning `max_features` (0.2) was the largest value offered, so larger
values were tested with all other settings held at the step 2 winners.

| `max_features` | `binary` macro-F1 | `family` macro-F1 |
|---|---|---|
| 0.1 | 0.9119 | 0.8223 |
| 0.2 | 0.9191 | 0.8278 |
| 0.3 | 0.9207 | 0.8262 |
| 0.4 | 0.9227 | 0.8280 |
| 0.5 | **0.9243** | **0.8289** |

0.5 was chosen. For `binary` the gain over 0.2 is 0.005, slightly more than
the standard deviation across folds (0.003 to 0.004). For `family` it is
0.001, well inside it (0.004 to 0.007). 0.5 is again the largest value tried;
larger values were not tested.

**Final settings, both tasks:** `n_estimators=300`, `max_depth=30`,
`min_samples_split=5`, `min_samples_leaf=2`, `max_features=0.5`,
`criterion="entropy"`, `class_weight="balanced"`, `random_state=42`.

### Step 5. Analysis (`src/random_forest/analysis.py`)

Done after the final test. It explains the finished model and changes no setting.

**Feature importance.** Two measures, for all 299 features:

- **MDI** (mean decrease in impurity): how much of the trees' splitting work
  each feature did during training. The values add up to 1.
- **Permutation importance**: how much test macro-F1 falls when one feature's
  values are shuffled so the model can no longer use it. It is measured on the
  test set.

Top five features by MDI:

| `binary` | MDI | Permutation | `family` | MDI | Permutation |
|---|---|---|---|---|---|
| `hdr_SizeOfImage` | 0.141 | 0.075 | `hdr_SectionAlignment` | 0.133 | 0.011 |
| `hdr_MajorLinkerVersion` | 0.095 | 0.074 | `sec_rsrc_Misc_VirtualSize` | 0.069 | 0.057 |
| `sec_rsrc_Misc_VirtualSize` | 0.065 | 0.028 | `dll_mscoree.dll` | 0.068 | 0.004 |
| `api_exit` | 0.059 | 0.003 | `hdr_Characteristics` | 0.051 | 0.018 |
| `hdr_DllCharacteristics` | 0.043 | 0.044 | `hdr_SizeOfCode` | 0.049 | 0.016 |

Share of MDI by feature group:

| Group | Features | `binary` | `family` |
|---|---|---|---|
| PE header | 30 | 49.7% | 49.1% |
| PE sections | 38 | 27.6% | 29.8% |
| API calls | 222 | 18.3% | 11.0% |
| Imported DLLs | 9 | 4.4% | 10.1% |

## 4. Why the compile date was removed

The first complete run used all 300 features, including `hdr_TimeDateStamp`,
the date the file was compiled. Its analysis showed that one feature did
**44% of the splitting work** in the `binary` model (MDI 0.437; the next
feature had 0.077) and was the second most important for `family` (0.118).

In the training data most malware was compiled in 2020 to 2022, while the
benign files are spread over earlier years. A compile date says when a file
was built, not what it does, and an attacker can set it to anything. A model
relying on it has learned how the dataset was collected, not how to recognise
malware. It was therefore excluded for every model, in `src/data.py`.

| | With the compile date | Without (final) | Change |
|---|---|---|---|
| `binary` CV macro-F1, baseline | 0.9620 | 0.9148 | -0.047 |
| `binary` CV macro-F1, tuned | 0.9720 | 0.9243 | -0.048 |
| `binary` test macro-F1 | 0.9742 | **0.9273** | -0.047 |
| `binary` test accuracy | 0.9925 | 0.9785 | -0.014 |
| `binary` test benign recall | 0.936 | 0.872 | -0.064 |
| `family` CV macro-F1, baseline | 0.8584 | 0.8219 | -0.037 |
| `family` CV macro-F1, tuned | 0.8678 | 0.8289 | -0.039 |
| `family` test macro-F1 | 0.8723 | **0.8325** | -0.040 |

The earlier run's result files are kept in `results/with_timestamp/random_forest/`.
Its models and figures were overwritten.

**To state in the report:** the Random Forest was scored on the test set
twice, once in each run. The second run was made to remove a flawed feature,
and its settings were again chosen by cross-validation on the training set
alone, not by looking at test scores.

## 5. Points for the Discussion section

- **Test scores match the CV estimates** (0.9273 vs 0.9243; 0.8325 vs 0.8289),
  so the model was not over-fitted to the training folds during tuning.
- **Accuracy flatters the `binary` task.** 0.9785 sounds strong, but the
  do-nothing baseline is 0.92. Macro-F1 (0.927) and benign recall (0.872) are
  the honest view.
- **Benign is the weak side of `binary`.** Only 8% of files are benign, and
  12.8% of them are flagged as malware. In real use false alarms on legitimate
  software are costly.
- **Removing the compile date cost about 5 points of detection macro-F1**
  (section 4). The lower score is the more trustworthy one.
- **The linker version was kept, and this should be disclosed.**
  `hdr_MajorLinkerVersion` is the second most important `binary` feature by
  both measures. It records which linker version built the file, so it is
  build metadata, and it correlates moderately with the removed compile date
  (Spearman 0.54). A feature audit (`src/feature_audit.py`, results in
  `results/feature_audit/`) retrained the forest without each of the 30 header
  fields in turn, using 100 trees and 5-fold CV on the training set. Removing
  the linker version lowered macro-F1 by 0.016 for `binary` and 0.013 for
  `family`, 2 to 4 standard deviations across folds and about a third of the
  compile date's effect. No other header field changed either score by more
  than 0.008. The team kept it because it identifies the toolchain, which is
  a property of how a malware family is built: 65% of RedLineStealer files use
  linker version 6, and 49% of SnakeKeyLogger and 61% of Spyware use
  version 48.
- **The benign and malware files differ in composition.** 27% of benign
  training files are 64-bit, against 0.4% of malware, and 37% of benign files
  import `exit` from the C runtime, against 1.7% of malware. The detection
  model can therefore partly separate the classes by architecture and runtime
  library. This is spread over many correlated features, so it cannot be
  removed by dropping columns; it is a limitation of the dataset.
- **Type classification is harder than detection** (macro-F1 0.83 vs 0.93).
- **Three types are confused with each other.** SnakeKeyLogger and Spyware
  swap most (183 and 148 files), and RAT leaks into both (71 and 52). All
  three monitor the user, so they plausibly share behaviour. This explanation
  has not been checked against the features.
- **Downloader and RedLineStealer are easy** (F1 0.96 and 0.95).
- **API calls and DLLs add almost nothing to detection for this model.**
  Header and section fields alone score 0.9222, against 0.9243 for all 299
  features. API calls and DLLs alone score 0.476, the same as always answering
  "malware" (0.479): the model then finds 94.9% of benign files but calls 47%
  of malware benign. One measured reason: 55% of benign training files have
  exactly the same API and DLL flags as at least one malware file, so those
  flags cannot separate them.
- **API calls and DLLs do carry information about malware type** (0.630 alone,
  against 0.061 for guessing), but header and section fields carry more
  (0.817 alone).
- **Detection rests on about 50 features.** Without the 50 most important,
  `binary` falls to 0.482, the level of the dummy model.
- **MDI and permutation importance disagree on some features.** For example
  `dll_mscoree.dll` ranks third by MDI for `family` but has almost no
  permutation importance, which suggests other features can stand in for it.
  MDI is known to favour features with many distinct values, so both measures
  are reported.
- **Tuning gave about one point of macro-F1** on `binary` and under one point
  on `family`, steps 2 and 3 together.

## 6. File reference

### Folder layout

Each model has its own folder under `src/`, `results/`, `models/` and
`figures/`, with the same name in all four. Code shared by every model sits
directly in `src/`.

```
src/
  data.py              shared data loader (leaves out hdr_TimeDateStamp)
  evaluation.py        shared cross-validation and score printing
  plot_style.py        shared chart colours and styling
  random_forest/       baseline.py, tune.py, max_features.py, final.py,
                       analysis.py, figures.py
  svm/                 the SVM scripts
results/random_forest/ every number the Random Forest scripts produce
results/with_timestamp/ results of the earlier run that included the compile date
models/random_forest/  the two trained Random Forests
figures/random_forest/ the five Random Forest figures
```

### Scripts, run in this order from the project root

| Script | Does | Time on a 24-core machine |
|---|---|---|
| `src/data.py` | Shared loader. `load_data("binary")` or `load_data("family")` returns `X_train, X_test, y_train, y_test`. `EXCLUDED_FEATURES` lists the columns no model receives. Not run directly. | n/a |
| `src/evaluation.py` | Shared by all models: the 5 folds, the class names, and the function that cross-validates a model and computes its scores. Not run directly. | n/a |
| `src/random_forest/baseline.py` | Step 1, baseline CV | about 15 s |
| `src/random_forest/tune.py` | Step 2, randomized search | about 6 min |
| `src/random_forest/max_features.py` | Step 3, `max_features` follow-up. Updates `tuned_params.json`. | a few minutes (not timed) |
| `src/random_forest/final.py` | Step 4, final training and test | under 1 min |
| `src/random_forest/analysis.py` | Step 5, feature importance and ablation | several minutes (not timed) |
| `src/random_forest/figures.py` | Step 6, the five figures | a few seconds |
| `src/plot_style.py` | Shared chart colours and styling. Not run directly. | n/a |

```
python src/random_forest/baseline.py
python src/random_forest/tune.py
python src/random_forest/max_features.py
python src/random_forest/final.py
python src/random_forest/analysis.py
python src/random_forest/figures.py
```

Everything uses seed 42.

### Results (`results/random_forest/`)

# SVM: what was done, what each file holds

This is the reference for writing the SVM section of the report. Every number
below comes from the files listed here, and every file can be regenerated by
running the six scripts in order.

It follows the same layout as `RANDOM_FOREST.md`. The tasks, the data split,
5-fold cross-validation, the standard deviation across folds and the metrics
are explained in sections 1 and 2 of that document and are not repeated here.

All results are **without the compile date** (`hdr_TimeDateStamp`), on the
same **299 features** as the Random Forest. Section 4 shows the
cross-validation scores from before it was removed.

## 1. The two tasks

| Task name | Question | Training set | Test set |
|---|---|---|---|
| `binary` | Is this file malware or benign? | 18,768 files (1,501 benign, 17,267 malware) | 4,693 files (375 benign, 4,318 malware) |
| `family` | Which of the 6 malware types is it? | 17,267 malware files | 4,318 malware files |

One SVM is trained per task.

## 2. Ideas needed to read the results

**Support Vector Machine (SVM).** A classifier that treats every file as a
point in space, with one axis per feature (299 axes here), and finds the
boundary that separates the classes with the widest possible gap (the
"margin") between them. A new file is classified by which side of the
boundary it falls on.

**Support vectors.** The training files that lie on or inside the margin.
They alone define the boundary; the other training files could be deleted
without changing the model. A model that needs many support vectors has a
complicated boundary, and it is slower, because every prediction compares the
new file with every support vector.

**Kernel, and the RBF kernel.** A kernel is the function the SVM uses to
measure how similar two files are. The RBF (radial basis function) kernel
scores similarity from the distance between the two files: 1 for identical
files, falling towards 0 as they get further apart. It lets the boundary be
curved instead of a flat plane. All SVMs here use the RBF kernel.

**Hyperparameter.** A setting chosen by us before training, as opposed to a
parameter, which the model learns from the data. The RBF SVM has two main
hyperparameters, `C` and `gamma`.

**`C` (regularisation parameter).** How heavily the SVM is penalised for
training files on the wrong side of the margin. A small `C` accepts some
misclassified training files in exchange for a simpler, smoother boundary. A
large `C` bends the boundary to classify more training files correctly, at
the risk of over-fitting.

**`gamma` (RBF kernel coefficient).** How quickly similarity falls with
distance, and so how far the influence of one training file reaches. A small
`gamma` gives a smooth boundary; a large `gamma` lets the boundary wrap
tightly around individual files, again at the risk of over-fitting.

**`class_weight`.** With `"balanced"`, mistakes on a rare class are penalised
more, in proportion to how rare it is. With `None`, every file counts the
same.

**Multi-class SVM.** An SVM separates two classes. For the 6 malware types,
scikit-learn trains one SVM for every pair of types (15 pairs, the
"one-vs-one" scheme) and the type that wins the most pairings is predicted.

**Feature scaling (preprocessing).** Because the SVM works on distances, a
feature with large values would dominate the distance and the others would be
ignored. Header and section fields range from 0 to billions; the API and DLL
flags are 0 or 1. Two preprocessing steps are therefore applied before the
SVM:

1. **Log transform**, `log(1 + x)`, on the 68 header and section columns. It
   compresses very large values, so a few huge values no longer dominate.
2. **Standardisation** (`StandardScaler`) on all 299 columns: each feature is
   shifted and rescaled to mean 0 and standard deviation 1.

The Random Forest needs neither step, because a tree only asks whether a
value is above or below a threshold.

**Pipeline.** scikit-learn's way of chaining the preprocessing steps and the
model into one object. Its purpose here is to prevent **data leakage**: in
cross-validation, the scaler's mean and standard deviation are computed from
each fold's training part only, never from the part being scored. The saved
model files contain the whole pipeline, so raw feature values can be passed
in directly.

**Random search and grid search.** Two ways of tuning. A random search draws
hyperparameter combinations at random from given ranges (30 combinations
here). A grid search tries every combination of fixed lists of values. Each
combination is scored by 5-fold cross-validation.

**Decision score.** For `binary`, the SVM's `decision_function` gives each
file a signed distance from the boundary: positive on the malware side,
negative on the benign side, and larger in size the further from the
boundary. It is the SVM's equivalent of a confidence value.

**ROC-AUC** (area under the receiver operating characteristic curve;
`binary` only). It measures how well the decision score ranks files: it is
the probability that a randomly chosen malware file receives a higher score
than a randomly chosen benign file. 1.0 is a perfect ranking and 0.5 is
random. Unlike accuracy and F1, it does not depend on where the boundary is
placed.

**Permutation importance.** The fall in test macro-F1 when one feature's
values are shuffled between files, so that the model can no longer use that
feature. An RBF SVM has no built-in importance measure (nothing equivalent to
the Random Forest's MDI), so this is the only measure used for the SVM.

## 3. The six steps and their results

### Step 1. Baseline (`src/svm/baseline.py`)

The pipeline with scikit-learn's default hyperparameters (`C=1`,
`gamma="scale"`) and `class_weight="balanced"`, scored by 5-fold CV.

| Task | Accuracy | Macro-F1 (+/- across folds) | Dummy macro-F1 (from the Random Forest baseline) |
|---|---|---|---|
| `binary` | 0.8458 | 0.7040 (+/- 0.0089) | 0.4792 |
| `family` | 0.7058 | 0.7144 (+/- 0.0139) | 0.0608 |

For `binary`, the default SVM found 95.9% of benign files but labelled 2,833
of 17,267 malware files (16.4%) as benign, which is why its accuracy is below
the 0.92 of always answering "malware".

### Step 2. Tuning by random search (`src/svm/tune.py`)

30 random combinations per task, each scored by 5-fold CV on macro-F1.

| Hyperparameter | Range offered | How it was drawn |
|---|---|---|
| `C` | 0.1 to 300 | at random, evenly on a logarithmic scale |
| `gamma` | 0.0001 to 0.1 | at random, evenly on a logarithmic scale |
| `class_weight` | balanced, None | at random |

| Task | Baseline | Best of 30 | Worst of 30 |
|---|---|---|---|
| `binary` | 0.7040 | 0.8955 | 0.6689 |
| `family` | 0.7144 | 0.7614 | 0.6018 |

The same combination won both tasks: `C` = 160.5, `gamma` = 0.0051,
`class_weight=None`.

- **Tuning matters far more for the SVM than for the Random Forest.** It
  gained 19 points of macro-F1 on `binary` and 5 on `family`; the forest
  gained about 1.
- **`class_weight="balanced"` was harmful for `binary`.** The best
  combination with it scored 0.7931, against 0.8955 without it (16 and 14
  combinations respectively). For `family` the difference was small (0.7537
  against 0.7614).

### Step 3. Follow-up on larger `C` (`src/svm/tune_large_c.py`)

The best `C` values in step 2 were near the top of the range offered (300),
so a grid search tested larger values, with `gamma` values around the best
found and `class_weight=None`: 15 combinations per task.

`binary` CV macro-F1:

| `gamma` \ `C` | 300 | 1,000 | 3,000 | 10,000 | 30,000 |
|---|---|---|---|---|---|
| 0.002 | 0.8878 | **0.8964** | 0.8921 | 0.8899 | 0.8868 |
| 0.005 | 0.8953 | 0.8940 | 0.8877 | 0.8828 | 0.8767 |
| 0.01 | 0.8701 | 0.8689 | 0.8703 | 0.8711 | 0.8651 |

`family` CV macro-F1:

| `gamma` \ `C` | 300 | 1,000 | 3,000 | 10,000 | 30,000 |
|---|---|---|---|---|---|
| 0.002 | 0.7619 | 0.7645 | 0.7662 | 0.7723 | 0.7733 |
| 0.005 | 0.7641 | 0.7718 | 0.7771 | **0.7779** | 0.7767 |
| 0.01 | 0.7656 | 0.7706 | 0.7735 | 0.7750 | 0.7748 |

- `binary`: the gain over step 2 is 0.0009, far below the standard deviation
  across folds (0.008). Larger `C` makes the score fall.
- `family`: the gain over step 2 is 0.0165, about 4 standard deviations
  across folds (0.004). The score peaks at `C` = 10,000 and falls slightly at
  30,000.
- Both best values lie inside the grid, not on its edge, so tuning stopped
  here.

**Final hyperparameters** (RBF kernel, `random_state=42`):

| Task | `C` | `gamma` | `class_weight` | CV macro-F1 (+/- across folds) |
|---|---|---|---|---|
| `binary` | 1,000 | 0.002 | None | 0.8964 (+/- 0.0076) |
| `family` | 10,000 | 0.005 | None | 0.7779 (+/- 0.0036) |

## 4. Effect of removing the compile date

The SVM baseline and both tuning steps were first run on all 300 features,
including `hdr_TimeDateStamp`, and then repeated without it. The final test
was only ever run without it, so **the SVM was scored on the test set once.**

| CV macro-F1 | With the compile date | Without (final) | Change |
|---|---|---|---|
| `binary` baseline | 0.7070 | 0.7040 | -0.003 |
| `binary` tuned | 0.9048 | 0.8964 | -0.008 |
| `family` baseline | 0.7145 | 0.7144 | 0.000 |
| `family` tuned | 0.7821 | 0.7779 | -0.004 |

The tuned hyperparameters with the compile date were `C` = 3,000,
`gamma` = 0.005 for both tasks. The earlier result files are kept in
`results/with_timestamp/svm/`.

The SVM lost under 1 point where the Random Forest lost about 5 (see
`RANDOM_FOREST.md`, section 4). The SVM was therefore relying on the compile
date much less. The reason has not been tested. One candidate is the log
transform: Unix timestamps for 2010 and 2022 differ by under 2% after
`log(1 + x)`, though standardisation then rescales that difference.

## 5. Points for the Discussion section

- **Test scores match the CV estimates** (0.8950 against 0.8964; 0.7785
  against 0.7779), so the hyperparameters were not over-fitted to the
  training folds.
- **The SVM is behind the Random Forest on both tasks**: test macro-F1 0.895
  against 0.927 for `binary`, and 0.779 against 0.833 for `family`.
- **The two models make opposite kinds of error on `binary`.** The SVM misses
  10 malware files where the forest misses 53, but it wrongly flags 116
  benign files where the forest flags 48. Which is preferable depends on
  whether a missed malware file or a false alarm is the more costly error.
- **Benign recall is the SVM's weak point** (0.691). 30.9% of legitimate test
  files are flagged as malware.
- **The SVM ranks files less well than the forest**: ROC-AUC 0.973 against
  0.993.
- **Accuracy hides the difference.** The SVM's `binary` accuracy (0.9732) is
  close to the forest's (0.9785), while macro-F1 differs by 3 points.
- **The same three types are confused, more severely.** 333 SnakeKeyLogger
  files are labelled Spyware and 154 Spyware files are labelled
  SnakeKeyLogger (183 and 148 for the forest). RAT recall is 0.657.
- **Downloader and RedLineStealer are easy for both models** (F1 0.96 and
  0.94 here).
- **Default hyperparameters are poor for the SVM.** The baseline scored 0.704
  on `binary`; tuning raised it to 0.896. A report that used an untuned SVM
  would understate it by 19 points.
- **`class_weight="balanced"` hurt `binary` detection** (best 0.793 with it,
  0.896 without). The baseline, which used it, shows the pattern: it found
  95.9% of benign files but placed 16.4% of malware files on the benign side.
- **The `family` model is much more complex than the `binary` model.** It
  keeps 53% of its training files as support vectors, against 7%, and needs
  `C` = 10,000. The boundaries between malware types are harder to draw than
  the boundary between benign and malware.
- **Header and section fields carry the SVM's detection ability, as for the
  forest.** With those 68 features alone it scores 0.898 on `binary`, the
  same as with all 299 (0.896; the difference is inside the standard
  deviation across folds). For `family`, removing the API and DLL features
  costs 1.4 points.
- **The SVM extracts more from API calls and DLLs alone than the forest
  does** for `binary`: 0.771 against the forest's 0.476. It still finds only
  40.8% of benign files that way.
- **The SVM's ability is spread over more features than the forest's.**
  Without its 50 most important features the SVM still scores 0.781 on
  `binary`; the forest fell to 0.482, the level of the dummy model. The two
  "top 50" lists are ranked by different measures (permutation importance
  here, MDI for the forest), so this comparison is indicative only.
- **Shuffling a group and removing a group give different answers.**
  Shuffling the 222 API-call features lowers `family` test macro-F1 by 0.367,
  yet retraining without the API-call and DLL features lowers CV macro-F1 by
  only 0.014. Permutation importance measures how much the trained model
  depends on a feature; ablation measures whether the information is
  available elsewhere. The model uses the API features, but header and
  section fields can replace almost all of what they provide.
- **The two models rank features differently.** `hdr_FileAlignment` is the
  SVM's most important `binary` feature; `hdr_SizeOfImage` is the forest's.
  Many header and section fields are correlated, so each model can reach a
  similar result through different ones.
- **The linker version matters less to the SVM** (12th for `binary`, fall
  0.032) than to the forest (2nd, fall 0.074). It is kept for all models and
  disclosed (see `RANDOM_FOREST.md`, section 5).
- **Cost.** The SVM is slow to analyse: permutation importance for the
  `family` model (single features and groups) took 44 minutes on 24 cores, because each prediction is
  compared with 9,163 support vectors.
- **To state in the report:** permutation importance was measured on the test
  set, and its ranking was used to choose which features to remove in the
  ablation. This is descriptive analysis after the final test; no
  hyperparameter or model was chosen from it.

### Models (`models/svm/`)

| File | Contents |
|---|---|
| `binary.joblib` | Trained benign-vs-malware pipeline (0.3 MB) |
| `family.joblib` | Trained malware-type pipeline (2.2 MB) |

Each file holds the whole pipeline, so it takes the raw feature values. Load
and use (needs scikit-learn 1.7.0, as pinned in `requirements.txt`):

```python
import joblib, sys
sys.path.append("src")
from data import load_data

model = joblib.load("models/svm/binary.joblib")
_, X_test, _, y_test = load_data("binary")
print(model.predict(X_test.iloc[:5]))            # 0 = Benign, 1 = Malware
print(model.decision_function(X_test.iloc[:5]))  # positive = malware side
```

The `family` model predicts the type numbers 1 to 6; `TYPE_NAMES` in
`src/data.py` maps them to names.
